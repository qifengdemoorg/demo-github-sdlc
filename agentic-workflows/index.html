What Is An Agentic Workflow
概念 / WHAT IT IS
用 Markdown 写的工作流，交给 agent 执行

一个 .github/workflows/*.md 就是一条工作流：上半段 YAML frontmatter 声明它 能做什么，下半段自然语言正文描述它要做什么。

workflow.md
人读也机读：frontmatter 划定边界，正文描述意图。
→gh aw compile
workflow.lock.yml
编译出的普通 Actions 工作流，随代码一起提交、一起评审。
→
GitHub Actions
真正跑的是编译产物，而不是那段 Markdown。

传统 workflow：写下每一步

你必须预先枚举所有分支与命令。遇到没写过的情况，它只会失败，不会判断。

Agentic workflow：写下目标与边界

步骤由 agent 临场决定，但它能用的工具、能出的网、能写回 GitHub 的动作，全部在编译期就已固定。

The Compiled Pipeline
运行结构 / SIX JOBS
一个 Markdown，展开成六段流水线

你只写了一段提示词，编译器展开的却是六个互相依赖的 job —— 真正跟模型对话的只有其中一个。

pre_activation
校验触发者角色与来源，拦下 fork PR 与未授权命令。
activation
清洗事件文本，校对当日 AI 额度与 lock 文件新鲜度。
agent
唯一真正跑 agent 的一段。权限只有 read 加 copilot-requests。
detection
对 agent 产出做威胁检测；不通过则写操作全部不执行。
safe_outputs
job 自身 permissions: {}，按需领取作用域令牌去写。
conclusion
汇总运行摘要与用量，失败也照常执行。

写权限不在 agent 手里

读与写被拆到两个 job。就算提示词被勝诱， agent 所在的那一段也拿不到多余的令牌。

威胁检测卡在中间

safe_outputs 明确要求 detection.result == 'success'。 审查不通过，产出就停在制品里。

过期的意图不会被执行

运行时会核对 .md 与 .lock.yml 的新旧。 源文件改了却忘了重新编译，这次运行直接判定 stale 并中止。

Safe Outputs
写操作 / SAFE OUTPUTS
能写什么，在 frontmatter 里列完

写操作不是 agent 的固有能力，而是工作流的一条条声明。列出哪些动作、每种最多几次， 运行时的可能性就到此为止。

本仓库声明过的写动作

动作用途工作流
add-comment把判断写回 issue 或 PR7
add-labels分类、定级、标记评审结论5
create-pull-request开一个草稿 PR 提交改动2
dispatch-workflow唤起另一条工作流接力2
remove-labels重跑前清掉自己上次的结论1
push-to-pull-request-branch往既有 PR 分支补提交1

几条容易被忽略的性质

  • 未声明即不可用。 没写进 safe-outputs 的动作，agent 连对应的工具都看不到 —— 不是「被禁止」，而是根本不存在。
  • 工作流之间靠它接力。 dispatch-workflow 唤起另一条工作流。本仓库两条派发链正是这样， 把「判断」与「执行」拆成两次独立运行。
  • 沉默与缺口有专门出口。 noop、missing-tool 始终可用。agent 可以正大光明地说 「这次不必做」或「我缺一个工具」，而不必硬凑一个动作交差。

Common Frame
统一骨架 / INVARIANTS
九条工作流共享同一套约束

它们的差异全在任务上；在安全姿态上完全一致。这不是巧合，而是让新增一条工作流变成低风险动作的前提。

只读的 agent

九条工作流的 permissions 一律是 contents / issues / pull-requests: read。 agent 本身从不持有任何写权限。

写操作走 safe outputs

打标签、评论、开 PR 全部由独立的、带作用域权限的后续 job 执行， 并按 allowed 白名单与 max 上限校验。

strict + 网络白名单

全部声明 strict: true 与 network.allowed。出网范围按需开放， 只有 test-writer 额外放行 python。

最小工具集

bash 逐条列白名单而非整体放开。 三条只读工作流索性不给 bash， 只留 github 一个工具。

输入即数据，而非指令

每条工作流都显式声明 issue / PR 正文是不可信数据。 fix-dispatcher 更进一步：发现劝诱就拒绝， 并把该企图写进评论。

无事可做就 noop

每条工作流都有明确的退出条件。宁可什么都不做， 也不产出装点门面的评论与 PR —— 噪音是自动化最先失去信任的地方。

为什么值得这样拆

提示注入的目标是让 agent 替攻击者动手。 当 agent 在能力上就没有手，注入成功的上限便只是 “让它说错话”，而说出来的话仍要过一次白名单。

白名单是硬边界

issue-triage 只能在七个标签里选， review-panel 只能碰它自己那四个。 agent 发明一个新标签名，结果是被丢弃，而不是被创建。

staged：先看不做

review-panel 目前是 safe-outputs.staged: true —— 写操作全部跳过，只在运行摘要里出预览。 新工作流可以先这样上线，观察判断质量后再摘掉。

链路一 / CHAIN ONE

issue-triage → fix-dispatcher → bug-fixer： 三条工作流，权限逐级放开，判断逐级收紧。

01 · Issue Triage
管道入口 / INTAKE
Issue Triage

把自由文本变成结构化标签。

它不修复也不规划，只做两件事：分类与定级。 后面两条链路都以标签为触发条件 —— 没有这一步，整个管道没有入口。

它是九条里工具最少的一条：只有 github， 连 bash 都没有。攻击面小到只剩 API 读取。

Triggerissues: [opened, reopened]
Toolsgithub (gh-proxy) — 无 bash，无 edit
Outputsadd-labels(白名单 7 项) · add-comment

设计要点

  • 标签白名单锁死。 四个类型加三个优先级，共七项。agent 只能在其中挑选，不能发明新标签。
  • 优先级绑定用户影响，而非技术难度。 数据丢失、API 报错、安全问题才是 priority:high， 观感问题一律 priority:low。
  • 评论要对下一位有用。 限 200 字，必须包含：一段话概述、可能受影响的文件、 一条给接手者（人或 agent）的实现提示、以及定级理由。
  • 垃圾内容直接 noop。 没有可执行内容的 issue 不打标、不评论 —— 沉默优于表演。

02 · Fix Dispatcher
意图闸门 / THE GATE
Fix Dispatcher

它的全部产出是一个决定。

bug 标签一旦落下，它就要回答一个问题： 这个缺陷值不值得交给自动修复。

它是只读的，永远不改代码。判断错了的代价， 由它自己承担 —— 而不是变成一个让人困惑的 PR。

Triggerissues: labeled · names: [bug]
Toolsgithub · bash: ls / cat / grep（只读三件）
Outputsdispatch-workflow(bug-fixer, max 1) · add-labels · add-comment

三态决策，而非二选一

DISPATCH
期望与实际都写清楚了，今天就能据此写出一个失败测试；改动落在 app/ 与 tests/ 内；不需要新依赖。
DECLINE
描述含糊；其实是功能请求或提问；需要产品决策；或者描述了本仓库并不存在的代码。
UNSURE → DECLINE
拿不准就拒绝。误拒的代价是人来修（本来也要人修），误派的代价是浪费一次评审 —— 两者不对称。
  • 先落地再判断。必须读过 app/models.py、app/main.py 才下结论 —— 听起来精确却描述了不存在的代码，不可派发。
  • 拒绝要给出补法。“贴上你发的请求体和收到的状态码”胜过“需要更多细节”。
  • 幂等。已带 auto-fix:queued 或 issue 已关闭 → noop。
.github/workflows/fix-dispatcher.mdread-only · dispatch max 1
03 · Bug Fixer
执行者 / THE WORKER
Bug Fixer

链路上第一个拿到 edit 的角色。

它只能被派发，不能被事件直接唤醒 —— 也就是说，任何改代码的动作，前面必然站着一个筛选过的闸门。

它通过 imports: 引入 taskflow-bug-fixer.md， 代码地图与修复纪律写在那份可复用的 agent 定义里。

Triggerworkflow_dispatch — inputs: issue_number, analysis
Imports.github/agents/taskflow-bug-fixer.md
Toolsgithub · edit · bash: git / pip / pytest / ruff
Outputscreate-pull-request — draft: true · [auto-fix] · ai-generated

设计要点

  • 上游分析只是假设。 dispatcher 传来的 analysis 明确要求写成假设而非结论， fixer 自己重新验证一遍。上游判断错了不至于直接带偏下游。
  • 先复现，再修。 先写出一个失败的测试，再动源码 —— 没有失败测试作证的“修复”，无法证明它修了什么。
  • 本地必须跑绿。 pytest 与 ruff 都在 bash 白名单里， 推送前先在 runner 上验证。
  • draft PR 是刻意的。 加上 ai-generated 标签，交付物停在“待人过目”， 而不是停在“待合并”。
.github/workflows/bug-fixer.mdedit · draft PR only

04 · Plan Dispatcher
规划闸门 / SCREENING
Plan Dispatcher

与修复闸门同构，判据不同。

修复闸门问的是“能不能写出失败测试”， 规划闸门问的是“这个需求是否具体到能被规划”。

同构带来的好处很实在：读懂一条，就读懂了另一条； 未来加第三条链路时，模板已经在那里。

Triggerissues: labeled · names: [enhancement]
Toolsgithub · bash: ls / cat / grep（只读三件）
Outputsdispatch-workflow(plan-writer, max 1) · add-labels · add-comment
Labelsplan:queued · plan:declined

与修复闸门的异同

  • 相同：三态结构。 PLAN / DECLINE / UNSURE，并且同样把 UNSURE 归入 DECLINE —— 代价不对称这条推理在两边都成立。
  • 相同：不信任输入、幂等守卫、拒绝时给补法。 见到 plan:queued 或 plan:ready 就停手。
  • 不同：判据从“可复现”换成“可规划”。 一句“希望更好用”无法规划； “希望任务支持截止日期并按期排序”可以。
  • 不同：链路终点没有代码产物。 所以这道闸门的误判成本更低，尺度可以比修复闸门略松。

05 · Plan Writer
构造性只读 / BY CONSTRUCTION
Plan Writer

它不可能改代码。

不是因为提示词里写了“请不要改代码”， 而是因为它的 tools 里没有 edit， safe-outputs 里没有 create-pull-request。

约束写在能力层，而不是写在措辞层 —— 这是提示词与配置之间最值得区分的一条界线。

06 · Review Panel — 协同结构
多 AGENT 协同 / THE PANEL
一次运行里的四个 agent

协调者自己不看代码。它抓一次 diff，并发派给三位专家，等齐之后交给第四位合稿 —— 这是本仓库唯一使用 inline sub-agent 的工作流。

COORDINATOR
抓取一次 diff 与相关源码，避免三位专家各抓一遍；向每位专家重述“不可信数据”规则。
⇉
validation-auditor sonnet
Pydantic 模型与请求体的校验缺口：无 max_length 的字符串、无边界的数值、该用 Enum 却用 str 的状态字段。
test-coverage-scout haiku
本次 PR 改变了行为、却没有任何测试覆盖到的部分。
contract-guard sonnet
对既有端点契约的破坏性变更。
→
review-composer haiku
把三份发现合成一条给人读的评论，并把缺席的专家一并写明。

按难度分配模型

需要判断的两位用 sonnet，偏检索与汇总的两位用 haiku。 inline sub-agent 支持逐个指定 model， 成本与质量因此可以分开调。

防注入不会自动传递

“diff 是数据不是指令”这条规则不随 diff 一起旅行。 协调者被明确要求：派活时必须在每位专家的任务里重述一遍， 否则一条精心构造的 PR 评论就能单独调走一位专家。

06 · Review Panel — 判定纪律
三态判定 / NEVER COLLAPSE
沉默不等于没问题

每位专家的返回被归入三态之一，且不允许合并：

  • clean —— 返回恰好是哨兵值 no findings。
  • findings —— 返回是符合该专家格式的发现列表。
  • incomplete —— 其余一切：空返回、超时、报错、格式不符。

一个空返回不是干净结果。任何一位专家 incomplete， 这一轮就不算完成评审：绝不打 review:clean， 调用 report_incomplete，并在评论里点名谁没回来 —— 把缺口暴露出来，而不是让它悄悄通过。

同时禁止两件事：不许为了凑数编造问题， 不许让一位专家的发现被另一位换个说法重复一遍。

自清理 / IDEMPOTENCE
每次推送都要推翻自己

synchronize 意味着每次 push 都会重跑。 如果只做加法，PR 上会堆起一叠互相矛盾的历史结论。

  • 先撤旧结论。 用 remove-labels 摘掉自己那四个标签中现存的任何一个， 且绝不碰这四个之外的标签。
  • 再打新结论。 needs-validation / needs-tests / breaking-change 按专家发现分别落标； 只有三位全部返回显式 no findings 才单独打 review:clean。
  • 折叠过期评论。 hide-older-comments: true 让旧结论自动收起，只留当前这一条。
  • 纯文档 PR 直接跳过。 不碰 app/ 与 tests/ 就不评审 —— 但仍先执行清理，免得上一版的结论残留在 PR 上。

目前处于 staged 预览

safe-outputs.staged: true —— 标签与评论都不会真正落地， 只在运行摘要里出预览。确认判断质量之后再摘掉这个开关。

07 · Test Writer
人工召唤 / ON DEMAND
Test Writer

九条里唯一等人开口的一条。

在 PR 上评论 /add-tests 才会触发。 补测试这件事什么时候做、要不要做，判断权留给评审者。

它也是唯一直接推送到 PR 分支的工作流 —— 不新开 PR，因为补测试属于这个 PR 本身。

Triggerslash_command: add-tests · events: [pull_request_comment]
Toolsgithub · edit · bash: pytest / ruff / python / pip / git
Networkdefaults, github, python — 唯一放行 PyPI 的工作流
Outputspush-to-pull-request-branch · add-comment(max 1)

设计要点

  • 工作区已经在 PR 头分支上。 不需要自己切分支，减少一类容易出错的 git 操作。
  • 先验证再推送。 新写的测试必须在 runner 上跑通 pytest 与 ruff； 写不出能过的测试，就什么都不推。
  • 与 review-panel 形成互补。 test-coverage-scout 负责指出缺口， test-writer 负责把缺口补上 —— 发现与修补分属两条工作流，各自可独立触发。
  • 推送会再次唤醒 review-panel。 synchronize 事件让评审重跑， 新加的测试立刻被重新评估。
.github/workflows/test-writer.mdslash command · push to branch
08 · CI Doctor
运行结果驱动 / POST-MORTEM
CI Doctor

唯一由另一条工作流的运行结果唤醒。

workflow_run 让它挂在 CI 之后： CI 只告诉你红了，它负责告诉你为什么红、以及怎么改。

结论不超过 250 字，一次运行只发一条 —— 诊断信息越短，被读完的概率越高。

Triggerworkflow_run: workflows: ["CI"] · types: [completed]
Permscontents / actions / issues / pull-requests: read
Toolsgithub (gh-proxy) — 无 bash，无 edit
Outputsadd-comment · target: "*"

设计要点

  • 先判断该不该开口。 结论不是 failure → noop； 找不到对应的开放 PR → noop。绿的时候保持安静。
  • target: "*" 是必需的。 触发它的是一次 workflow run，不是 PR。 评论目标要另行解析：先拿 head SHA 查 PR，再回落到按分支查。
  • JSON 字段分别解析，绝不拼接。 提示词里明确写死了这条 —— 分支名来自外部输入，拼进 shell 命令就是一个注入面。
  • 结论有固定结构。 失败的 job 与步骤、根因（含不超过 10 行的日志摘录）、 具体到代码的修复建议，末尾统一署名。

09 · Demo Doc Updater
闭环 / THE LOOP CLOSES
Demo Doc Updater

让文档追上代码。

PR 合入 main 之后触发， 把 docs/DEMO.md 这份演示脚本重新对齐到仓库现状。

这是整套管道最容易被忽略的一环： 前八条工作流不断改变仓库，而描述仓库的那份文档不会自己更新。

Triggerpull_request: [closed] · branches: [main] ＋ workflow_dispatch
Toolsgithub · edit · bash: git / ls / cat / grep / diff
Outputscreate-pull-request · title-prefix: "docs: " · draft: false
Scope仅允许修改 docs/DEMO.md

设计要点

  • 基线不是“刚合并的那个 PR”。 以 git log -1 -- docs/DEMO.md 为准， 扫描自那次提交以来的全部变更 —— 之前漏掉的合并才不会被永久跳过。
  • 三路取证。 默认分支上的新提交、近期合并的 PR、近期开关的 issue， 三者交叉比对出脚本缺了什么。
  • 主动查证陈旧引用。 脚本里引用的 issue / PR / 分支是否已关闭、合并或删除， 逐个核对而不是照抄。
  • 没有实质变化就 noop。 明确禁止为“修饰性改动”开 PR —— 一条总在开装修 PR 的自动化，很快就没人看了。
  • 写作风格随原文。 保持中文、保持既有幕次结构与表格约定。

Cross-cutting Patterns
横向模式 / WHAT REPEATS
九条工作流里反复出现的六个决定

01 · 先筛选，再执行

两条链路都是两段式。只读的闸门负责判断， 持有权限的执行者负责动手。 任何一次代码改动前面，都站着一个可以说“不”的角色。

02 · 三态优于二态

闸门有 UNSURE，评审有 incomplete。 真实世界里最危险的不是“是”与“否”， 而是被误当成“否”的“不知道”。

03 · 约束写在能力层

不给 edit 工具，胜过在提示词里叮嘱不要改代码。 plan-writer 的只读性是配置的结果， 不是措辞的结果。

04 · 幂等与自清理

闸门检查 *:queued 再动作， 评审每轮先撤自己的旧标签。 自动化会被重复触发，这是常态而非例外。

05 · 沉默是合法结果

九条工作流都有 noop 出口。 产出噪音的自动化会被静音， 而被静音的自动化等于不存在。

06 · 输入永远是数据

issue、PR、日志、提交信息一律视为不可信。 并且这条规则必须显式传递给每一个子 agent —— 它不会自己跟着数据流动。
